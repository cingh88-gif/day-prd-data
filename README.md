# day-prd-data

iERP **공정진척현황(작업보고) `PM60250Rv3`** 에서 지정 작업반의 **전날치**를 엑셀출력으로
받아 모으고, **일마감 진행률 보고서**를 만든다. 매일 정해진 시각에 자동으로 돈다.

`ierp-prod-report`(일일생산실적 PM60230Uv3) · `ierp-manhour`(공수 PM40510Uv3) 와 같은 구조다.
그쪽에서 실측으로 얻은 win32 접근·Excel COM 저장·재접속 로직을 그대로 이식했다.

## 집계 규칙 (사용자 확정)

| 항목 | 정의 |
|---|---|
| 제외 | 오더상태 **30작업지시** 건 |
| 모수 | **50작업진행 + 80작업완료** |
| 일마감 진행률 | **80작업완료 ÷ 모수** |
| 건수 단위 | **작업지시번호 기준 distinct** (공정별로 여러 행이 내려와도 1건) |

> **왜 화면에서 30을 미리 안 거르나.** 조회조건으로 빼 버리면 30이 몇 건이었는지 알 수 없어,
> *수집이 덜 된 것*인지 *원래 30이 많았던 것*인지 구분이 안 된다. 그래서 **ALL 로 받아서
> 집계에서** 거르고, 제외한 건수까지 보고서에 남긴다.

`M2102` · `J2001` · `M2107` · `M1101` · `M1102` · `M1104`

GUI 에서 켜고 끄고 추가/삭제할 수 있다. 이름이 빈 작업반은 **첫 수집 때 iERP 가 돌려준
작업반명으로 자동으로 채워진다.**

## 전제

- **수집은 Windows 전용.** 집계·보고서(`aggregate.py`/`report.py`)는 WSL 에서도 돈다.
- iERP 는 **사용자가 직접 로그인**해 둔 상태 — **iEMenu** 가 떠 있어야 한다.
- iERP 와 **권한을 맞춘다** (iERP 를 관리자로 띄웠으면 이 도구도 관리자로).
- 수집 중에는 마우스/키보드를 만지지 말 것 (키 입력이 iERP 창으로 들어간다).

### 2) 실행


## 이 화면을 다루는 핵심 원칙 (형제 프로젝트 실측 이식)

**UIA 깊은 탐색을 절대 하지 않는다.** 그리드에 수천 행이 차면 컨트롤 하나 찾는 데:

| 방법 | 소요 |
|---|---|
| win32 `EnumChildWindows` | **0.00초** |
| UIA 깊은 탐색(`child_window`) | 63초 뒤 **실패** |

그래서 컨트롤은 ① win32 로 **찾고** ② 핸들 바인딩 UIA(`ElementFromHandle`, O(1))로
**읽고 누른다.**

**조회가 끝났는지도 그리드를 읽어서 판단하지 않는다.** 조회 중에는 앱이 메시지 펌프를
멈추므로(제목에 `(응답 없음)`), `SendMessageTimeout` 으로 **앱이 살아났는지**만 본다.

## 알려진 함정

| 함정 | 대응 |
|---|---|
| 조회가 끝나기 전 엑셀출력 → **행 수는 맞는데 전부 빈 칸** | `wait_responsive` 로 앱 응답을 기다린 뒤 출력 |
| iERP 가 시트 **크기를 먼저 잡고** 값을 나중에 채움 | `UsedRange` 크기만 보지 않고 `CountA` 까지 3회 연속 같을 때만 저장 |
| DTP 를 `DTM_SETSYSTEMTIME` 으로 바꾸면 표시만 바뀜 | 실제 키 입력 후 **읽어서 확인**. 화살표 이동은 순환이라 안 씀 |
| **작업반 입력이 안 먹은 채 조회** → 다른 작업반 데이터가 그 작업반 파일로 저장 | 코드 입력 후 **읽어서 대조**하고, 저장된 파일의 작업반 열까지 다시 대조 (`verify_saved`) |
| 엉뚱한 날짜를 그 날짜 파일로 저장 | 조회 **직전에** 화면 날짜를 한 번 더 대조 |
| 빈 파일을 남기면 재개 때 건너뜀 | 검증 실패 시 **파일을 지우고** 실패 처리 (Excel 이 놓을 때까지 재시도 삭제) |
| 매 출력마다 빈 Excel 껍데기가 쌓임 | `cleanup_excel()` — 단 **사용자 Excel 은 보호**(`guard_excel`) |
| 연달아 조회하다 화면이 죽음 | 2개 연속 실패하면 화면 재접속. 안 하면 남은 작업반이 전부 몇 초짜리 실패로 소진됨 |
| **프로그램ID 를 `PM60250R` 로 열면 안 열림** | 버전 접미사까지 — **`PM60250Rv3`**. 검색창이 남으면 `열기` 버튼 폴백 |
| **`작업완료 포함`(chkSELOPT1)이 꺼진 채로 뜬다** | 그대로 조회하면 **80작업완료가 통째로 빠져 진행률이 매일 0%** 로 나온다. 화면을 새로 열 때마다 꺼지므로 **매 실행 시작에 켜고 읽어서 확인**한다. 못 맞추면 수집을 아예 시작하지 않는다 |
| **`개시예정일` 시작 칸이 비어 있어 타이핑이 통째로 무시된다** | `CustomFormat=" "` 라 편집할 날짜 구역 자체가 없다. `DTM_SETSYSTEMTIME`(프로세스 경계 못 넘음)·Legacy SetValue·ValuePattern 전부 막혀 있었다. **▼(달력) 클릭 → Enter** 로 값을 살린 뒤에야 타이핑이 먹는다 (`materialize_dtp`) |
| **Edit 값을 `window_text()`/`GetWindowText` 로 읽으면 항상 빈 값** | 값이 멀쩡히 들어 있는데도 ''로 읽혀 "작업반이 안 들어갔다" 고 오판했다. **UIA ValuePattern → WM_GETTEXT** 순으로 읽는다 (`_edit_text`) |
| **`Excel 정리` 직후 포커스가 흔들려 작업반 입력이 사라진다** | 다음 작업반 코드가 안 들어가고 **이전 값이 남는다.** 입력 직전에 창을 다시 앞으로 가져오고, 값을 읽어 확인한 뒤 **최대 3회 재시도**한다 |
| **Excel 이 COM 호출을 거부(`RPC_E_CALL_REJECTED`)** | 사용자가 열어 둔 Excel 이 바쁘면 난다. 예외를 삼키면 "Excel 없음" 으로 5분간 조용히 기다리다 실패한다 → 짧게 재시도하고, 끝까지 거부하면 **어느 창이 거부했는지 로그에 남긴다** |
| 보고서를 열어 두면 다음 실행에서 같은 이름으로 저장 불가 | 저장 전에 **그 워크북만** 닫는다(`close_workbook_at`). 그래도 안 되면 시각을 붙여 저장하고 알린다 |

## 실측 소요시간 (2026-09-01, 대상일자 2026-08-31)

작업반 1개당 **20~25초**(조회 7초 + 엑셀출력·저장 대기). **12개 작업반 = 약 3~4분.**
0건인 작업반도 같은 시간이 든다(조회·출력을 똑같이 하므로).

첫 실행 결과: 저장 5 · 0건 7 · 실패 0. 12개 중 7개가 0건이었다 —
**개시예정일이 그 날인 작업지시가 없는 작업반**이다.

## ⚠️ 확인이 필요한 것

1. **`개시예정일` 기준이 맞는지.** 이 화면의 기간 조건은 작업일자·보고일자가 아니라
   **개시예정일**이다. "전날 데이터" 가 *어제 개시예정이던 작업지시들의 진척* 이 맞는지
   확인이 필요하다. (2026-08-31 기준 12개 작업반 중 7개가 0건이었다)
2. **실행 시각** — 11시/12시 미정. `실행.bat` GUI 에서 정해 등록하면 된다.
